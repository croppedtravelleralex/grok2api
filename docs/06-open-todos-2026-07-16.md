## TODO-2：Cloudflare 403 — 直连 vs Webshare / 拒因深挖

| 项 | 内容 |
| --- | --- |
| Backlog | MTN-007（证据 Done）/ MTN-005（换出口 Planned）/ MTN-008（udeal） |
| 优先级 | P0 |

| 探针 | `newapi/tools/grok-cf-deep-diagnose.py`、`grok-cf-udeal-fresh-sample.py` |

### 已核实结论（2026-07-16）

| 出口 | plain HTTP `https://grok.com` | 结果 |
| --- | --- | --- |
| 本机 `203.10.99.34`（机房 GSL AS137409，非家宽） | 200，`<title>Grok</title>`，~419KB | **pass_app**；PoP `NRT`；**无** `cf-mitigated`；有 `cf-cache-status: DYNAMIC` |
| panda 直连 `43.156.233.219`（腾讯云 AS132203） | 403，`Just a moment...`，~5.6KB | **Managed Challenge** |
| Webshare 抽样 5 个 | 全部 403 + CF | 同左 |
| udeal 早盘 80 条 | `ok_200=3`（QmFKV/ff4G/qQtT） | 偶发可过 |
| udeal 深挖时再测原「ok」3 会话 | 全部 403 Managed Challenge | **粘滞 IP 已漂 / 信誉不稳定** |
| udeal 新鲜随机 40 条 | `pass_app=1` / challenge=31 / connect_fail=6 / other_403=2 | 仍有苗头但稀 |

### 拒因分类（深挖，非猜）

被拒页统一特征（panda + 多数 udeal）：

| 信号 | 含义 |
| --- | --- |
| HTTP **403** | 被拦，不是超时 |
| 响应头 `cf-mitigated: challenge` | Bot Management **挑战**，不是硬封 |
| 正文 `cType: 'managed'` | **Managed Challenge**（需 JS/浏览器求解） |
| `<title>Just a moment...</title>` + `Enable JavaScript` + `__cf_chl` | 标准 CF interstitial |
| 挑战页额外头 | `cross-origin-opener-policy: same-origin`、`cross-origin-embedder-policy: require-corp` |
| 仍发 `__cf_bm` cookie | 有 bot 管理 cookie，**不等于已过关** |
| **未见** Turnstile / `Attention Required` / `You have been blocked` | 当前主路径不是人机勾选页，也不是永久硬封文案 |

通过页（本机 + 偶发 udeal）对照：

| 信号 | 含义 |
| --- | --- |
| HTTP **200** + `<title>Grok</title>` + ~400KB+ | 真应用壳 |
| **无** `cf-mitigated` | 未被 challenge 拦截 |
| 有 `cf-cache-status: DYNAMIC` | 走应用源，非挑战页 |
| 应用 `permissions-policy` 为 camera/mic 等 | 与挑战页「全禁用」策略不同 |
| 正文仍可能出现 `challenge-platform` 字符串 | **正常**（前端带 CF SDK），不能单凭此判失败 |

### 关键结论

1. **拒因类型 = Cloudflare Managed Challenge**（`cType=managed`），不是「网站挂了」或简单 WAF 硬封。
2. **本机 200 ≠ 家宽**：双方都是机房段；差异在 **具体 ASN/IP 段信誉 + CF 评分**，不是「机房 vs 宽带」二分。
3. **住宅/ISP 标签不够**：udeal 出口可落在 Singtel/Starhub/MyRepublic 仍被 `managed`；偶发通过例：`session=6XIJ` → egress `82.47.112.28`（AS402289 Webgist / GB），PoP `MRS`，复测仍 200。
4. **ok session 不可当永久白名单**：QmFKV 等几小时后同 session 已变 challenge；必须 **实时筛池** 或加长粘滞 + 浏览器 canary。
5. plain HTTP 过关只证明出口信誉；生产 Web 仍需浏览器/HTTP 逆向求解或携带 clearance。

### 后续 AC

1. 至少 1 个实时 `pass_app` 出口在 **browser-bridge canary** 下完成 grok.com 加载。
2. 筛池脚本保留 `cf-mitigated` / `cType` / `pass_app` 三元组，淘汰仅「TCP 通」。
3. 文档持续更新成功/失败 ASN 样本（见 MTN-008）。

| 项 | 内容 |

| 优先级 | P0 |

### 对照事实

- 参考实现：panda `/root/gptimage`（chatgpt2api）
  - 传输：`curl_cffi` + `impersonate=chrome*`
  - 鉴权：access_token + sentinel chat-requirements
  - 生图：ChatGPT `backend-api` conversation/files/tasks（HTTP/SSE）
  - 浏览器：FlareSolverr **仅 CF 清障**，非每请求起 Chrome
- 现状 grok2api：Web/imagine 强制 `browser-bridge`（undetected Chrome），有请求时峰值 ~76% CPU / ~500MB+

### 验收标准（AC）

1. 完成 grok.com Web/imagine 相关抓包清单（URL、header、cookie、关键步骤）。
2. 最小 PoC：在可用出口下，用不经每请求 Chromium 的 HTTP 客户端完成至少一次 chat 或 imagine。
3. 网关侧有开关：`bridge`（旧）/ `http_reverse`（新）；失败可回退。
4. Panda 上同负载资源占用明显低于 bridge（记录 docker stats 对照）。

### 风险

- 不能照搬 ChatGPT `backend-api` 路径；Grok 接口需单独逆向。
- 无合格出口时，HTTP 逆向仍会被 CF 拦；与 TODO-2 出口问题耦合。

# grokImage 项目最终目标定义

## 项目愿景

把 Grok Build、Grok Web 和 Grok Console 的授权账号组织为可观察、可恢复、可控并发的统一 API 网关，并向 NewAPI 等调用方提供稳定的 OpenAI/Anthropic 兼容接口。

## 目标用户

- 需要统一管理多来源 Grok 账号池的项目 Owner。
- 通过 Chat Completions、Responses、Messages、Images 和 Videos 接口调用 Grok 的内部系统。
- 负责账号导入、额度、代理、故障恢复和请求审计的运维人员。

## 最终完成态定义

- 三类 Provider 独立路由、独立状态、独立额度和清晰的失败原因。
- 对话、生图、图片编辑和视频接口可以被标准客户端稳定调用。
- Web/Build 账号支持可审计的导入、刷新、隔离和有限恢复，不把已撤销凭据伪装成可恢复。
- 图片历史可展示、筛选、下载、按日期清理，并保留生成元数据。
- Panda 只运行经过本地测试和 CI 构建的受限容器，不承担源码构建和大并发批任务。

## 成功标准

- 关键后端测试、前端 lint/build 和生产单请求 canary 均有新鲜证据。
- 失效账号不会进入请求调度池，错误原因能指导下一步操作。
- Web 请求和刷新有明确并发上限，不因批量任务压垮 Panda。
- 数据删除、凭据操作和生产部署都有确认、回滚和日志边界。

## 当前明确不做的内容

- 不绕过上游服务条款、风控或授权边界。
- 不承诺用已撤销的 Build Refresh Token 纯 HTTP 恢复账号。
- 不在 Panda 上编译、构建镜像、跑全量浏览器并发或无界刷新；构建只在本机/CI，Panda 只下载已构建产物。
- 不为了隐藏错误而自动删除失效账号。

## 长期质量底线

- 安全底线：凭据加密存储，日志和文档不记录明文 Token、Cookie、密码或代理口令。
- 状态底线：可用、失效、禁用、额度耗尽和待重新授权必须分开表达。
- 文档底线：关键事实以代码、配置、数据库、测试和生产证据为准，并同步回写 `docs/`。
- 维护底线：本地优先；Panda 变更必须执行容量预检、单单元 canary、资源限制和回滚验证。
